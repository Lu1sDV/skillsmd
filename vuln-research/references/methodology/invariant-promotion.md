# Invariant Promotion — closing the learning loop

> **What this is.** The procedure for promoting a confirmed, reusable *triage invariant* learned during a campaign into the canonical skill, so the next campaign on **any** target inherits it inline. This is the durable, cross-target write-back that the v2 pipeline rewrite dropped and that **Phase 6 — Invariant Promotion** (`commands/vuln-swarm.md`) restores. Without it, every campaign re-learns the same caps (consumer gate, reachability cap, hardened-allocator OOB→DoS, server-crash-on-deployed-surface, DoS-scope) and writes them only to per-target memory the skill loader never reads.

---

## Why the loop was broken

Lessons from a campaign land in **per-target sinks** — the run's DuckDB, project memory, retro/audit docs — none of which the **durable, cross-target** skill loader reads. There was a producer (campaigns) and a consumer (the skill) wired to **different buses**, and **nothing failed** when a confirmed invariant was never promoted. A recommendation is inert unless something *fails* when it is absent. Phase 6 + the `v_invariant_promotion_coverage` gate make non-promotion **fail the completion gate**; this doc is the procedure that gate enforces.

---

## The durable sink

The single durable, cross-target home for a promoted invariant is:

```
references/methodology/triage-invariants.md
```

an **append-only registry** loaded at Phase 0 Decompose and Phase 2 Confirm so every lane sees the caps inline. Each row is shaped (owned/defined by that file):

```
INV-id | invariant (agnostic statement) | trigger condition | severity effect |
        evidence (target + finding ids that proved it) | generalized-from (the target-specific lesson) |
        skill-location (which gate/doc enforces it) | promoted-in (skill version)
```

> `triage-invariants.md` itself is created and owned by a separate workstream. This doc references it by name and describes how Phase 6 writes into it; it does not define its schema beyond the row shape above.

---

## The promotion procedure (Phase 6)

At end of campaign, after Phase 5 Report, for every

```sql
SELECT * FROM agent_observations
WHERE obs_kind = 'invariant' AND reusable = TRUE AND confidence = 'high'
```

that does **not** already map to a `triage-invariants.md` row, do **one** of the two below.

### Option A — Open a promotion entry (atomic; all four parts)

A promotion is **incomplete** unless all four land together:

1. **Generalize, then append.** Restate the lesson as a **target-agnostic** invariant — the cited target (e.g. a columnar database, a hardened-libc++ build) becomes *evidence*, never the rule. Append one `INV-id` row to `references/methodology/triage-invariants.md`.
2. **Enforce it.** Edit the matching **gate / doc** the invariant should govern (a reference doc, a phase doc, or a gate view in the schema tier). A registry row with no enforcement edit is catalogued-but-unenforced — exactly the audit-doc-graveyard failure. Record the edited location in the row's `skill-location` field.
3. **Bump the version.** Increment `SKILL.md` frontmatter `version:` (and the command's, per the house wiring rules). Stamp it into the row's `promoted-in` field.
4. **Append a CHANGELOG line.** In `CHANGELOG.md`, canonical form:

   ```
   vX.Y.Z — promoted INV-id (learned in <campaign>, finding ids …) → <gate/doc edited>
   ```

   This is the ledger that makes "learned N times, promoted 0 times" **detectable** instead of invisible, and gives the loop an owner (whoever lands the CHANGELOG line owns the promotion).

### Option B — Record a `promotion_skipped` reason

If the invariant should **not** be promoted, record an explicit, durable `promotion_skipped` reason — e.g. *already covered by `INV-007`*, *target-specific and does not generalize*, *duplicate of a pending entry*. A silent non-promotion is not allowed; the gate stays red until either a promotion entry or a skip reason exists.

### The gate

`v_invariant_promotion_coverage` (HARD RED, owned by the schema/harness tier) is **red while any** high-confidence reusable invariant has **neither** a promotion entry **nor** a skip reason. The run does not declare done while it is red. Phase 6 is the only phase that clears it.

## Canonical-only write rule

There are multiple copies of this skill. Edits must go to **exactly one**:

| Copy | Role | Edited by Phase 6? |
|---|---|---|
| **Canonical** — `/home/x/Personal_Projects/vuln-research` (`Lu1sDV/main`) | develop here; source of truth | **YES — the only write target** |
| **Vendored** — `find-ctfs/.agents/skills/vuln-research` | the copy a session actually loads | **NO — never hand-edited; regenerated by re-sync** |

**Rule:** every Phase 6 edit (`triage-invariants.md`, the gate/doc edit, the version bump, `CHANGELOG.md`) lands in **canonical only**. A write to the vendored copy never upstreams to canonical; a write to canonical does not reach the running session until a re-sync runs. Editing the vendored copy directly is the documented way lessons get lost.

> House landmine (carried from the wiring rules): **never `git add .` at the `find-ctfs` root** — it would stage the vendored tree. Stage canonical paths explicitly.

---

## The vendored re-sync step

After promotions land in canonical, the vendored copy is **regenerated from canonical** — it is a generated artifact, not an edit target:

1. Land all Phase 6 edits in canonical and confirm the version bump + CHANGELOG line are present.
2. Re-sync the vendored `find-ctfs/.agents/skills/vuln-research` tree **from** canonical (copy/overwrite from canonical, do not merge hand edits in the other direction). The vendored copy after re-sync is byte-identical to canonical for the promoted files.
3. The harness preflight (`vrdb selftest`, owned by the harness tier) warns when the loaded vendored `SKILL.md` version is **behind** canonical's `min_skill_version` — so a campaign never silently runs guardrails weaker than canonical. A vendored copy that is behind after a promotion means the re-sync was skipped.

---

## The loop, end to end

```
campaign ─> high-confidence reusable invariant  (agent_observations: obs_kind='invariant', reusable, confidence='high')
        ─> Phase 6 gate (v_invariant_promotion_coverage) is RED until promoted-or-skipped
        ─> Option A: append triage-invariants.md + gate/doc edit + version bump + CHANGELOG line   (CANONICAL only)
           Option B: record promotion_skipped reason
        ─> re-sync vendored from canonical; preflight enforces vendored ≥ min_skill_version
        ─> next campaign on ANY target loads the cap inline at Phase 0 Decompose / Phase 2 Confirm
```
