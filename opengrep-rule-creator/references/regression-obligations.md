# Regression obligations and skill evaluation

**Status:** Required authoring/test obligations, not implemented handlers or measured results. Documentation-only revisions do not authorize scanner, benchmark, provider or corpus execution. Mechanical preservation checks, when recorded, establish document identity—not semantic validity or detection accuracy.

## Two independent kinds of expected result

For every case retain source/contract assumptions, claim identity, scope, responsible rule(s), expected candidate admission, expected claim assessment, and actual execution receipt independently. `ruleid` or `ok` supplies only a native matcher expectation. A deliberately admitted safe candidate is not a false vulnerability verdict; an unsafe omitted candidate is not a safe negative.

Do not use one universal truth label for every effect in a file. A shell claim may be refuted while another process-related claim remains open. Conditional factories require concrete caller binding or an explicit justified educational contract before receiving a definite security label.

Before drafting question prose, the existing authoring handoff MUST record proposition, operation/value-version/consumer/path-state binding, actual supplied evidence, logical role, support witness, complete refutation, missingness and permitted decision use. These are authoring records, not new runtime fields. Ask whether a correct answer could still authorize a wrong verdict; STOP that use until its sufficiency gap is repaired.

## Required case shapes

| Dimension | Required contrasting situations | Prevented failure |
|---|---|---|
| API/call binding | Positional/keyword/default/known expansion/unknown expansion; direct/alias/callback/factory | Spelling-based FP/FN and assumed runtime identity |
| Operand | Same external value in dangerous versus inert argument, tuple slot, field or key | Whole-call/whole-object taint promotion |
| Reaching state | Trusted→untrusted and untrusted→trusted; relevant→unrelated and reverse; conditional mutation | Stale construction/assignment assumptions |
| Control | Effective, absent, unenforced, wrong subject, rejection swallowed, alternate valid control | Presence-based or patch-shaped safety |
| Representation/context | Safe original context, reinterpretation, later decoding/recomposition, accepted-domain change | Non-durable sanitizer summaries |
| Effect timing | Before/after control, eager/lazy, used/unused, constructed/delivered | Retroactive safety and false effect claims |
| Paths/consumers | One unsafe feasible witness; all protected; mixed protected/unprotected; incompatible branches | Invalid joint inference or partial refutation |
| Coverage | Responsible rule, companion, replacement pack, previously supported nonbenchmark form | Delegation gaps and scope loss |
| Evidence | Missing key, present-but-incomplete, contradictory, stale, irrelevant, malicious comment | Forced answers, leakage and fabricated completeness |
| Execution | Syntax failure, skip, timeout, budget exhaustion, duplicate candidate, transport failure | False clean results and hidden unassessed work |
| Claim boundary | Construction anchor versus required root; permitted query grammar versus unintended injection; unknown input role | Invented permissions or overstated mechanism observations |
| Narrow refutation | Fixed input-invariant origin or no external command content; request-controlled selection/cwd contrast | Requiring irrelevant business policy or treating constants as universal safety |
| Actual security consumer | Primitive used for security versus nonsecurity use; threat-specific protection; session storage versus authority; XML document without query consumer | API presence upgraded to a stronger claim or fabricated positive |
| Same-witness composition | Separate existential witnesses; same witness; one refuted witness with another surviving | Invalid conjunction or incomplete refutation |
| Bounded source facts | Known local builtin/name rebinding versus object mutation; constant list/dict slots across supported mutations; literal ordered match and guards | AST identity mistaken for semantic analysis |
| Unsupported semantics | Unknown aliases, custom operations/calls or unsupported flow | Guessed values or execution of target expressions |
| Rendered question | Instructions + criteria + supplied state; unsent top-level claim; string prose versus unsupported object instructions | Valid schema mistaken for answerable question |

Apply every relevant dimension, and record why a dimension is not applicable. Do not require a full Cartesian product for every rule; require intentional combinations where mechanisms interact. In particular, challenge **reassignment + sliced access**, **safe serialization + changed response context**, **container mutation + selected operand**, **control + post-check transformation**, and **rule-local exclusion + companion handoff**.

## How to test each trace

[Structured error traces](error-traces.json) supply T01–T42, linked to E01–E42 and gates G01–G12. Convert an obligation into an inert fixture or an actual integration test only after its API/runtime premises are supplied. Test both the responsible rule and selected pack where coverage composition is relevant. Keep tests designed to detect a vulnerability mechanism separate from native parser/admission probes.

For procedural paths, cover both justified positive and justified negative conclusions with a transport that fails if called. Zero requests plus the correct claim-specific result is the acceptance condition. An unsupported procedural shape does not automatically enter the model queue.

For model paths, test actual serialized input and answer-domain interpretation using labeled synthetic transport responses for orchestration only. Those responses do not establish model accuracy. Any live study requires separate source-upload authorization and a frozen protocol. Inspect source-derived evidence completeness independently of JSON shape.

MUST review rendered truth tables before any live study. Include false necessary-premise rows, incompatible witnesses, missing context, all-alternative refutation and a complete support witness. Independently derive semantic contrasts; do not let wording or expected model answers define truth. In profile 0.4 use string instructions and criteria, retaining labeled prose where useful. If testing option order, first prove changed serialized bytes; canonical sorting may erase source-order differences.

For proposed source-fact handlers, retain scope, method/version, source identity, operation/value version, supporting witness or exhaustive refutation and unsupported-domain receipts. Byte/AST integrity and bounded semantic validation are separate gates. No corpus execution, unknown alias assumption or custom operator invocation is permitted to obtain truth.

Procedural zero-call expectations require a validated applicable handler **and** reviewed versioned completion/routing path. A mandatory graph must not be completed by a fabricated Choice or an unexecuted node. Missing straightforward handlers retain the normal engineering blocker; an explicitly authorized bounded research exception may assess adequate source evidence in shadow mode without claiming deployment compliance. Missing essential consumer/policy evidence remains unresolved under either profile.

## Gate ledger

Each gate records `required_for_declared_scope`, `status` (not_run, blocked, passed, failed), artifact and source identities, actual invocation/condition, observed results, and unresolved limitations. Model execution status and security assessment remain separate. These are proposed authoring-side fields, not invented OpenGrep/JEV syntax.

MUST include a distribution receipt in that existing handoff: authoritative skill path, content revision/hash, applicable reference hashes, loaded consumer path/hash and explicit permitted profile/authorization. Local equality does not establish published equality. Do not create loader/runtime fields to hold this documentation. Failed gates remain visible even when independent authorized research can proceed; this ledger is not proof a semantic linter exists.

Promotion requires all required in-scope gates to pass. A conditional challenge cannot be converted into a guaranteed vulnerability solely to manufacture a failure, and an unsafe required failure cannot be moved out of sight to manufacture a pass. A documented scope change preserves the former obligation and its resulting coverage impact.

## Evaluation population and disposition obligations

Freeze official matchers, mappings and the entire scoring population. Supplemental discovery and matcher repairs are separate conditions. Audit every contributing finding in a unit; distinguish retained official FP units from newly introduced FP units. Eligibility expansion for unassessed official findings is by claim/evidence suitability, not Boolean truth, and includes TP controls. In an authorized derived comparison, omit an official alert only after an approved refutation of its own claim; retain unassessed, unresolved or conflicting official alerts. Supplemental positive emission requires its approved support gate; refuted, unresolved or conflicting candidates are not supported detections. Preserve raw supported/refuted/unresolved dispositions even for rejected candidates. One parse judgment is not refutation of all unit alerts.

Separate same-claim wording/decomposition, changed claim boundaries, evidence/procedural changes, official-coverage expansion and combined arms. Report incorrect support/refutation/unresolved assessments separately from end-to-end TP/FP/FN/TN, abstentions, provider failures, invalid responses, cost and workload. Development concentrations prioritize review only; numerical targets never override semantic truth or define a detector predicate. Retain all frozen units, including unassessed ones.

Check numerical guards algebraically before describing independent corroboration: for three Choice options, `c = (3 * p_max - 1) / 2`, so support `> .75` entails `c > .625`; a `.60` confidence floor adds no guard. Preserve `.75` when the frozen current research protocol requires it, not as a universal skill cutoff. Derived confidence is not calibrated correctness. No threshold tuning or empirical improvement is authorized by this document.

## Test whether the revised skill actually improves authoring

Use the same agent/tool setup on paired tasks under the original and revised skill, with fixed resource and permission budgets. Start each task with a clean context; randomize assignment/order where appropriate and keep groups of related templates/pairs together. Review outputs without revealing the instruction condition when practical.

Use independently reviewed hidden tests that target the mechanisms above, not exact phrases in the new skill. Include tasks where the correct outcome is a native repair, a procedural augmentation, a residual question, a request for missing evidence, or no defensible rule. Keep the original OWASP cases as development evidence, and use unrelated held-out cases for generalization.

Evaluate rule-level and whole-pipeline false positives/false negatives, preserved old coverage, invalid syntax/contracts, unjustified claims, unresolved/blocked handling, evidence integrity, unnecessary model requests, and analyst/model cost. Report partial outcomes, failures and instruction regressions; measure both task success and failure-severity profiles rather than ranking by rule count or prose compliance.

Predeclare criteria and meaningful non-regression bounds appropriate to the use case; none are measured or calibrated by this document. If the revised skill produces fewer unsafe exclusions but more unbounded candidates, report both rather than declaring unconditional improvement. Finite success does not establish zero error.

Keep fresh held-out groups independent of development templates and compare cold-start old-versus-new skill **and question authoring**. Distinguish constructs, equivalent wordings and evidence scopes in wording studies. The core's worked hybrid example is inert teaching material: parse its Python and request-shaped JSON only when an offline check is authorized; do not execute its source, send its synthetic request or count its author-reviewed table as an observed gate pass.
